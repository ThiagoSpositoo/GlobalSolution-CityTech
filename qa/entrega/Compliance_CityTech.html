Cidadãos registram e acompanham ocorrências; gestores realizam triagem, atualização de status e consulta de indicadores. A classificação por IA é consultiva e depende de supervisão humana. 2. Plano Scrum

Organização proposta

  • Product Backlog: 5 Epics → 12 Features → 39 PBIs, priorizados pelo valor ao cidadão, dependências e risco.
  • Sprints: ciclos curtos com objetivo verificável; refinamento prévio de descrição, aceite e dependências.
  • Planejamento: seleção de PBIs prontos, decomposição técnica e definição da capacidade.
  • Acompanhamento: Daily para progresso, impedimentos e coordenação entre Mobile, APIs, dados e QA.
  • Review: demonstração do incremento funcional com evidências reais.
  • Retrospectiva: ações de melhoria incorporadas ao ciclo seguinte.

Definition of Ready

Descrição compreensível, critérios de aceite objetivos, dependências identificadas, dados de teste fictícios e tamanho compatível com a Sprint.

Definition of Done

Código revisado, validações automatizadas pertinentes aprovadas, critérios atendidos, integração verificada, documentação atualizada e evidência real registrada. Item planejado ou bloqueado não é declarado concluído.

Estratégia de qualidade

Os testes são funcionais de caixa-preta, com um caso positivo e um negativo por Feature. Cada caso registra objetivo, preparação, entradas, saída esperada e passos estruturados. A criação e os vínculos foram verificados no Azure; execução manual e resultados no Test Plans são estados distintos e não são inferidos.

4. Features — descrição e aceite

ID 7Epic 2

FEA-01 Cadastro de Usuário

Permitir que cidadãos criem uma conta CityTech com nome, e-mail único e senha protegida. O cadastro público cria exclusivamente o papel CIDADAO, exige chave de idempotência e persiste a conta no SQL Server sem devolver senha ou hash.

Critérios de aceite

  • Cadastro válido retorna HTTP 201 com ID, nome, e-mail, papel CIDADAO e data de criação.
  • Nome, e-mail ou senha inválidos retornam HTTP 400 com erros por campo; e-mail duplicado retorna HTTP 409.
  • A repetição com a mesma Idempotency-Key e corpo não duplica a conta, e nenhum segredo aparece na resposta.

PBIs: 19, 20, 21, 22

ID 8Epic 2

FEA-02 Login e Autenticação

Autenticar contas ativas pela API .NET e emitir JWT RS256 consumido pelo Mobile, .NET e Java. A sessão protege rotas por papel e propriedade; o logout é local. Recuperação de senha não pertence ao MVP implementado e permanece planejada.

Critérios de aceite

  • Credenciais válidas retornam HTTP 200 com token Bearer, expiração e dados públicos do usuário.
  • Credencial inválida, token ausente, expirado, adulterado ou com claims inválidas retorna HTTP 401 sem revelar se o e-mail existe.
  • Logout remove a sessão do app e bloqueia rotas protegidas; recuperação de senha permanece identificada como não implementada.

PBIs: 23, 24, 25, 26

ID 9Epic 3

FEA-03 Cadastro de Ocorrência

Permitir que um cidadão autenticado registre problema urbano na API Java com título, descrição, categoria ativa, prioridade opcional e endereço textual. A criação persiste no Oracle, inicia em ABERTA, grava histórico e evento de outbox.

Critérios de aceite

  • Payload válido retorna HTTP 201, Location, UUID, prioridade definida e status ABERTA.
  • Campos inválidos ou categoria inexistente/inativa retornam HTTP 400 ou 409 e não criam ocorrência.
  • A ocorrência criada pertence ao sub do JWT, possui histórico CRIACAO e evento OccurrenceCreated.v1 no outbox.

PBIs: 27, 28, 29, 30

ID 10Epic 3

FEA-04 Anexo de Imagens

Planejar anexos fotográficos opcionais para ocorrências com seleção, validação e armazenamento seguro. Esta Feature não está implementada no backend nem no Mobile atual; o cadastro textual funciona sem imagem e nenhum upload deve ser apresentado como concluído.

Critérios de aceite

  • O cadastro de ocorrência continua funcional sem imagem, pois o anexo é opcional.
  • Antes da implementação, tentativas de upload não devem ser simuladas nem persistidas como se houvesse armazenamento.
  • Quando implementada, a solução deverá validar tipo, tamanho e vínculo, armazenar somente referência segura e rejeitar arquivo inválido sem criar associação.

PBIs: 31, 32, 33

ID 11Epic 3

FEA-05 Geolocalização e Endereço

Registrar e exibir a localização da ocorrência por endereço textual estruturado: logradouro, número, bairro, cidade, UF e CEP opcional. GPS, mapa, geocodificação e validação externa de CEP não estão implementados.

Critérios de aceite

  • Endereço válido é aceito na criação e retornado no detalhe da ocorrência.
  • UF inválida, campos obrigatórios ausentes ou CEP informado fora do formato retornam HTTP 400.
  • A interface exibe o endereço textual persistido sem alegar coordenadas, mapa ou validação por serviço externo.

PBIs: 34, 35, 36

ID 12Epic 4

FEA-06 Classificação Automática

Analisar a descrição da ocorrência no consumidor assíncrono e sugerir uma categoria válida com apoio do corpus RAG. A sugestão é consultiva, registra fontes e somente altera a ocorrência após revisão humana; sem modelo externo, o estado FALHOU é explícito.

Critérios de aceite

  • Evento consumido produz no máximo uma sugestão por eventId e a categoria sugerida pertence ao catálogo ativo.
  • Sugestão pronta registra fontes, modelo e versão do prompt e não altera automaticamente a ocorrência.
  • Falha, timeout ou saída inválida gera estado FALHOU e mantém a classificação manual disponível.

PBIs: 37, 38, 39

ID 13Epic 4

FEA-07 Priorização Automática

Sugerir prioridade BAIXA, MEDIA, ALTA ou CRITICA com base na descrição e nos critérios versionados do corpus. A prioridade de IA permanece separada da prioridade efetiva até decisão humana.

Critérios de aceite

  • Sugestão pronta contém somente prioridade permitida e justificativa rastreável.
  • Aceitar a sugestão aplica a prioridade com histórico e versionamento; rejeitar mantém o valor atual.
  • Saída fora do enum, sugestão já revisada ou versão concorrente é recusada sem alteração indevida.

PBIs: 40, 41, 42

ID 14Epic 4

FEA-08 Resumo Automático

Gerar e persistir resumo curto da ocorrência como parte da sugestão de IA, usando a descrição como dado não confiável e o contexto recuperado. O resumo auxilia a triagem, não substitui o relato original.

Critérios de aceite

  • Sugestão pronta contém resumo dentro do limite do contrato e vinculado à ocorrência correta.
  • Resumo, justificativa, fontes, modelo e promptVersion são persistidos e retornados no detalhe.
  • Conteúdo malicioso, resposta inválida ou modelo indisponível não executa instruções e resulta em falha controlada.

PBIs: 43, 44, 45

ID 15Epic 5

FEA-09 Consulta de Ocorrências

Permitir consulta paginada, filtrada e detalhada das ocorrências. Cidadãos veem somente recursos próprios; gestores veem a fila completa. O detalhe reúne endereço, status, categoria, prioridade, versão e sugestão disponível.

Critérios de aceite

  • Listagem válida retorna HTTP 200 com paginação, ordenação e filtros permitidos.
  • Cidadão recebe somente ocorrências cujo citizenId corresponde ao sub; tentativa de acessar ocorrência alheia retorna HTTP 404.
  • Detalhe válido retorna dados atuais e não expõe senha, token ou informação pessoal desnecessária.

PBIs: 46, 47, 48

ID 16Epic 5

FEA-10 Atualização de Status

Permitir ao gestor conduzir a ocorrência pelas transições autorizadas e ao cidadão confirmar ou reabrir quando a regra permitir. Cada alteração usa versão otimista e registra histórico. Notificação push não está implementada; a atualização fica visível nas consultas e no Mobile.

Critérios de aceite

  • Transição permitida retorna HTTP 200, incrementa version e registra ator, estados, nota e instante no histórico.
  • Transição inválida retorna HTTP 409; papel insuficiente retorna HTTP 403; versão antiga retorna HTTP 409 sem alterar o estado.
  • O status atualizado aparece na consulta e no Mobile; nenhuma notificação push é alegada no escopo atual.

PBIs: 49, 50, 51

ID 17Epic 6

FEA-11 Dashboard Gerencial

Disponibilizar ao gestor indicadores agregados de ocorrências por status e categoria, tempo médio de triagem e estatísticas de IA. O Mobile atual apresenta indicadores e contagens; gráficos visuais avançados permanecem planejados.

Critérios de aceite

  • Gestor recebe HTTP 200 com total, agrupamentos e generatedAt UTC coerentes com uma amostra conhecida.
  • Cidadão recebe HTTP 403 e nenhuma informação gerencial.
  • Conjunto vazio retorna zeros e coleções coerentes, sem erro ou divisão por zero; gráficos não implementados são identificados como pendência.

PBIs: 52, 53, 54

ID 18Epic 6

FEA-12 Relatórios Operacionais

Planejar relatórios operacionais consultáveis e exportáveis a partir de dados consolidados. Atualmente existem endpoint de indicadores e relatórios acadêmicos reproduzíveis em Oracle/MongoDB, mas não existe endpoint de geração/exportação de arquivo no produto.

Critérios de aceite

  • Os indicadores e scripts acadêmicos existentes produzem resultados sobre dados fictícios e rastreáveis.
  • A ausência de exportação no produto é registrada como pendência e não é demonstrada como funcionalidade concluída.
  • Quando implementada, a exportação deverá respeitar filtros, autorização de gestor, formato definido e ausência de dados pessoais desnecessários.

PBIs: 55, 56, 57

5. Product Backlog Items

ID 7 — FEA-01 Cadastro de Usuário

ID 19

PBI-001 Informar Nome Completo

Como cidadão, quero informar meu nome no cadastro para que minha conta tenha identificação de exibição.

Critérios de aceite
  • Nome com 2 a 120 caracteres é aceito.
  • Nome ausente ou fora do limite retorna HTTP 400 com erro no campo name.
  • O nome persistido é retornado sem qualquer dado de senha.
ID 20

PBI-002 Informar E-mail

Como cidadão, quero informar um e-mail válido e único para utilizá-lo como identificador de login.

Critérios de aceite
  • E-mail válido é normalizado antes da persistência.
  • Formato inválido retorna HTTP 400.
  • E-mail já cadastrado retorna HTTP 409 EMAIL_ALREADY_EXISTS e não cria segunda conta.
ID 21

PBI-003 Informar Senha

Como cidadão, quero definir uma senha no cadastro para autenticar minha conta com segurança.

Critérios de aceite
  • Senha entre 8 e 128 caracteres, contendo letra e número, é aceita.
  • Senha fraca retorna HTTP 400 com erro por campo.
  • A senha é armazenada somente como hash e nunca aparece em resposta ou log.
ID 22

PBI-004 Persistir Cadastro

Como plataforma, quero persistir o cadastro de forma idempotente para manter conta única e recuperável no SQL Server.

Critérios de aceite
  • Cadastro válido persiste uma Account com UUID, papel CIDADAO e timestamps UTC.
  • Mesma chave e corpo reproduzem a resposta sem duplicação.
  • Mesma chave com corpo diferente retorna HTTP 409 IDEMPOTENCY_CONFLICT.

ID 8 — FEA-02 Login e Autenticação

ID 23

PBI-005 Validar Credenciais

Como plataforma, quero validar e-mail e senha de uma conta ativa sem revelar qual credencial está incorreta.

Critérios de aceite
  • Credenciais corretas de conta ativa são aceitas.
  • Senha incorreta, e-mail inexistente ou conta inativa retorna HTTP 401 com mensagem genérica.
  • Nenhum token é emitido em tentativa recusada.
ID 24

PBI-006 Realizar Login

Como usuário, quero realizar login para receber uma sessão autenticada e acessar recursos permitidos ao meu papel.

Critérios de aceite
  • Login válido retorna accessToken, Bearer, expiresIn e usuário público.
  • JWT usa RS256 e contém sub, roles, iss, aud, exp e jti válidos.
  • O mesmo token válido é aceito pelas APIs .NET e Java.
ID 25

PBI-007 Encerrar Sessão

Como usuário Mobile, quero encerrar a sessão para remover o token local e impedir novo acesso pelas rotas protegidas.

Critérios de aceite
  • Logout remove token e dados de usuário do armazenamento seguro.
  • Após logout, rota protegida redireciona para login.
  • O MVP deixa explícito que o JWT já emitido permanece válido no servidor até expirar.
ID 26

PBI-008 Recuperar Senha

Como usuário, quero recuperar acesso caso esqueça a senha. Este fluxo está planejado, mas não existe endpoint, envio de e-mail ou tela de recuperação no MVP implementado.

Critérios de aceite
  • A funcionalidade permanece identificada como não implementada e não é simulada na demonstração.
  • Nenhum endpoint público revela se um e-mail está cadastrado.
  • Quando implementada, deverá usar token temporário, expiração, uso único e senha armazenada somente como hash.

ID 9 — FEA-03 Cadastro de Ocorrência

ID 27

PBI-009 Selecionar Categoria

Como cidadão, quero selecionar uma categoria ativa ao registrar a ocorrência para orientar sua triagem.

Critérios de aceite
  • O formulário lista categorias ativas retornadas pela API Java.
  • Categoria ativa é persistida no registro.
  • Categoria inexistente ou inativa é recusada sem criar ocorrência.
ID 28

PBI-010 Informar Descrição

Como cidadão, quero descrever o problema urbano para fornecer contexto à gestão e à sugestão de IA.

Critérios de aceite
  • Descrição entre 20 e 2000 caracteres é aceita.
  • Descrição ausente ou fora do limite retorna HTTP 400.
  • O texto é tratado como dado não confiável e não executa instruções.
ID 29

PBI-011 Informar Endereço

Como cidadão, quero informar o endereço textual da ocorrência para localizar o problema sem depender de GPS.

Critérios de aceite
  • Logradouro, número, bairro, cidade e UF válidos são obrigatórios.
  • Complemento e CEP são opcionais.
  • Campos inválidos retornam HTTP 400 e não persistem ocorrência parcial.
ID 30

PBI-012 Registrar Ocorrência

Como cidadão autenticado, quero concluir o registro para obter um protocolo UUID e acompanhar a ocorrência.

Critérios de aceite
  • Criação válida retorna HTTP 201 e Location.
  • Status inicial é ABERTA e prioridade omitida assume MEDIA.
  • Ocorrência, histórico CRIACAO e outbox são gravados atomicamente.
